# G6 — the gated hosted promotion runner (development and full-scale rehearsal)

**Status: DEVELOPMENT ONLY. NOT AUTHORIZED FOR ANY HOSTED WRITE.** Merging this change publishes code, nothing else: the shipped build pins **one owner signing subkey** (`OWNER_SIGNING_FINGERPRINTS`: `86F2D7601CBF30BE47536EDD9819DB56B663821E`, Ed25519 `[S]`, expires 2027-11-04; the primary `47AB7918…7355` is certify-only and not pinned). The pin alone authorizes nothing: every write still needs a fresh owner-signed authorization and a separately authorized release. No hosted database was contacted, no production backup was taken, no grant, import, promotion, withdrawal, refresh, Vercel change or migration (001–034 are untouched) is part of this change.

**What the signature gate is, and is not.** The real root of trust for a production write is custody of the production database password: anyone who holds `BAI_SUPABASE_DB_PASSWORD` can connect with `psql` and bypass this tool entirely, and anyone who can edit a local checkout can add their own key to the pin list. The signature gate is protection against operator error, scripted or AI-driven action and unreviewed code paths, and an audit trail (the signed file, the attempt records and the database ledger); it is not a barrier against a malicious holder of the credential. If that is not enough, the database itself must check something only the owner holds (for example a signed token verified in SQL), which needs a new migration and is not part of this change.

The local tool (`scripts/db/promotion.mjs`, `scripts/db/lib/promotion.mjs`) is **unchanged in behaviour**: it still refuses every non-local database and `--hosted`. The hosted runner is a separate, narrow entrypoint.

## 2. Security architecture and threat model

Assets: the production database (a promotion makes ~95,000 rows of third-party historical data public through the website at commit), the owner's authority over what is published, the integrity of the baseline (65 MLB trades withheld, existing players), the Retrosheet attribution obligation, and the production credential.

| Threat | Control | Residual risk |
| --- | --- | --- |
| A developer, script or AI session performs a hosted write without the owner (operator error, not a malicious credential holder: see above) | every write needs a JSON authorization with a **detached OpenPGP signature** by a key whose fingerprint is **pinned in the repository**; the runner host holds only the owner's public key (a keyring with a secret key is refused); nothing in this repository can sign; the pin list names exactly one signing subkey | the owner's signing key and the production password are the roots of trust; both are outside this tool; revocation of a signing key works only through the pin list (a revocation certificate imported into the runner keyring is also honoured); expiry and windows use the host clock |
| A signed authorization is replayed or used for something else | it binds operation, project, manifest, a ≤24 h window, a 128-bit nonce and (promote) the backup, parity record, attribution evidence and the exact REST-visible delta; it is consumed on this host before the first write (`O_EXCL`, in a directory taken from the account database, owned by the user, mode 0700, not from `$HOME`), so a second use is refused even in a parallel process; gpg verifies exactly the bytes that are parsed and hashed (fed on stdin, never re-read) | the consumed-artifact ledger is per host and a replay of an unconsumed, still-valid emergency/revert/finish/analyze authorization on ANOTHER host is stopped only by the database state and the 24-hour window (promote and withdraw are final in the database); the database's own manifest state (PROMOTED cannot be promoted again, WITHDRAWN never) is the final word |
| Man-in-the-middle or a look-alike host | `sslmode=verify-full` semantics through node-postgres (`rejectUnauthorized: true`, `servername` = the project host), the **pinned Supabase Root 2021 CA** (identity, CA flag, validity, SHA-256 fingerprint), host derived from the 20-character project reference only (`db.<ref>.supabase.co:5432`), no URL, no pooler, TLS ≥ 1.2, password only in the client configuration (never argv, URL or log; redacted from errors); `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_*`, `NODE_OPTIONS`, every `PG*` variable and every connection-URL variable make the runner **refuse to start** | the pinned CA expires 2031-04-26 (the check demands ≥ 30 days left) |
| A pooler or proxy silently drops the startup options | after connecting, the server is asked for its own `lock_timeout` and `statement_timeout`, encryption (`pg_stat_ssl`), database, user and port; anything but 5 s / 120 s / TLS / `postgres` / `postgres` / 5432 closes the connection | none known |
| A long-running or contended write holds production | session `lock_timeout` 5 s (covers the preflight and every read), `statement_timeout` 120 s, `idle_in_transaction_session_timeout` 5 min. **The write functions of migration 032 (`promote_begin`, `withdraw_promotion`, `emergency_withdraw`, `finish_withdrawal`) set their own `lock_timeout` of 15 s inside their transaction**, so the real lock wait of a write is up to 15 s, during which their pending lock requests queue behind a long reader and block newer readers of those tables | a statement near the limit fails the operation (atomic); measured times are in section 7 |
| A lost connection hides the outcome and an operator or script repeats a committed promotion | no retry anywhere; an unclear result is resolved on a **new read-only connection** by asking the ledger (polling while a writer session is still active); the attempt record says COMMITTED, NOT_PROMOTED_CONFIRMED or UNKNOWN; another attempt needs a new owner authorization that names the earlier attempt (`after_attempt`) | an UNKNOWN result needs a human with `status` |
| Wrong, stale or tampered inputs | package re-verified file by file; manifest ledger = hosted ledger exactly (and the Supabase history agrees; 031 absent); every one of the 94 scope tables fingerprinted against the manifest baseline inside a repeatable-read read-only transaction; backup ≤ 6 h with verified encrypted off-site evidence and a parity record ≤ 10 min made from the backup tool's verified record; live attribution evidence recomputed and ≤ 72 h old; grant row bound by hash; 65 MLB transactions; empty transaction read models; no other manifest; the database repeats the drift check inside the promotion transaction (`promote_begin`) | — |
| Publication is wider than the owner understood | the runner computes, from the catalog, every relation a Data API role could read after the promotion (tables by privilege, owner-rights views over them) and the owner's signed file must list exactly that set with row counts (section 6) | a new public relation added later is caught by the next preflight, not retroactively |
| Emergency close-api switches off public endpoints and website pages | the authorization must carry `acknowledge_site_outage: true` (a draft starts with `false`); the impact is documented (section 7) and needs its own owner authorization at execution time | the outage is real by design |

Not a control, stated plainly: the rehearsal could not exercise the real Supabase platform (pooler, gateway rate limits, hosted timings), and the shipped build cannot be used until the owner pins a key. The local `assertLocalTarget` remains the only protection of the old tool; it was not weakened.

## 3. Owner authorization contract

One file per operation, `bai-promotion-authorization/1`, plus `<file>.sig` (detached OpenPGP signature of the exact bytes). Fields: `format`, `operation` (`promote | withdraw | emergency | finish | revert | analyze`), `project_ref`, `manifest_sha256`, `not_before`, `expires_at` (window ≤ 24 h), `nonce` (≥ 32 hex), `after_attempt` (null or the id of the earlier attempt the owner has seen), and:

* **promote**: `backup {name, t0, manifest_sha256, archive_sha256, content_tree_sha256, offsite_record_sha256}` (all equal to the parity record's, which must itself come from the backup tool's verified off-site record), `parity_record_sha256`, `attribution_evidence_sha256`, `rest_public_delta [{relation, rows, by}]` (Data API roles) and `website_visible_delta [{relation, rows, by}]` (the website role `bai_site`, which is where the identities actually become public).
* **withdraw / emergency / finish / revert**: `reason`; withdraw may set `options.with_grant`; emergency may set `options.close_api` and then must set `options.acknowledge_site_outage: true`.
* **analyze**: planner statistics only.

`promotion-hosted.mjs draft-authorization` writes an **unsigned** draft filled from the files and a read-only look at the database, for the owner to read field by field and sign with their own key (`gpg --detach-sign`); `check-authorization` verifies a signed file offline. A developer-made approval is therefore impossible by construction: the tool has no signing code and no private key.

**Owner key:** the owner added a dedicated signing subkey (`86F2D760…821E`, expires 2027-11-04) to the certify/encrypt primary `47AB7918…7355`; its public part is in the runner keyring (`~/.config/bai-release/gnupg`, public keys only) and its fingerprint is pinned in `OWNER_SIGNING_FINGERPRINTS`. Pinning the subkey, not the primary, means no other subkey the primary may gain later is trusted. Replacing or rotating the key needs a new reviewed commit.

## 4. The hosted connection

`hostedClientConfig` / `connectHosted` build the connection from the project reference alone and prove it from the server's side (section 2). `tests/db/promotion-hosted-tls.test.mjs` drives the **real node-postgres client** against local PostgreSQL servers presenting: a trusted CA with the right name (accepted; TLS 1.3; session timeouts 5 s / 2 min arrive), a self-signed certificate, a certificate from an untrusted CA, a certificate for another host name, a server with TLS switched off, the wrong CA file for a good server, a wrong password, a closed port, a path that drops the startup options (a pooler) and a longer `lock_timeout` than allowed (all refused), and proves that `NODE_TLS_REJECT_UNAUTHORIZED=0` in the real process environment does not loosen it. The rehearsal cluster itself ran with TLS 1.3 and SCRAM and all rehearsal traffic used this code path.

## 5. Operations, failure semantics and the CLI contract

`promote` (all of it before the first write): package → authorization (signature, fields, window, nonce unused) → attribution evidence file (recomputed hash, statement on every page, deployment and commit named, ≤ 72 h) → parity record (≤ 10 min, backup ≤ 6 h, off-site evidence, level 034, this package) → the authorization's hashes equal those files → **connect** → hosted preflight (section 2) → REST delta equals the acknowledged one → attempt recorded and artifact consumed → **one** transaction (`promote_begin`, `promote_load` per table, `promote_withhold`, `promote_commit`, `commit`) → read-only post-verification (state, ledger rows per table, 94 fingerprints against the release state, 65 MLB trades, empty read models and unchanged read-model bookkeeping, one grant, REST delta).

Failure classes: only an ERROR the server itself raised (a pg `DatabaseError` with severity ERROR and a SQLSTATE outside classes 08, 57P, 58 and XX) is `ROLLED_BACK` (and the ledger is still asked once, as a cross-check). Everything else is `AMBIGUOUS`: Node socket codes that look like SQLSTATEs (`EPIPE`, `EBUSY`), FATAL/PANIC messages, connection-exception and operator-intervention classes, client-side timeouts. The connection is destroyed and a new read-only connection observes the manifest: writer sessions of the runner are counted before and after the state is read twice, and the answer is trusted only if there was no writer at either end and the state did not change (`PROMOTED` → `COMMITTED`; `NOT_PROMOTED` → `NOT_PROMOTED_CONFIRMED`; otherwise `UNKNOWN`, re-examined by `status` only for attempts older than a minute and only under the same rule). In every case the report says that **nothing was retried**. Exit code 0 only for a verified success; 1 for a refusal, a failure, `verify-promoted` with problems or a promotion whose post-verification failed (the JSON report on stdout says which); 2 for a usage error. A repeat of a FAILED attempt needs the owner's authorization to name it (`after_attempt`); an unresolved attempt blocks everything until `status` resolves it; a successful earlier operation does not block a new, separately authorized one (a real incident after a false alarm), and a committed promotion is never repeated. The parity record and the attribution evidence are checked again just before the first write (the preflight takes seconds), and a package that allows evidence older than 72 hours is refused.

**`verify-promoted` is lifecycle-aware (R8A).** It reads the read-model lifecycle from the database's own records, never from a flag: `PROMOTED` (no refresh or withdrawal recorded) expects every read-model table empty; `REFRESHED` (the latest event is a refresh) expects a populated model that agrees with the refresh record, the overview (generation, published, withheld and verified-complete totals), a single generation on the published rows, display categories that hold a publication grant (or are one of the four openly licensed groups) and no orphaned transactions; `WITHDRAWN` (the latest event is a withdrawal) expects empty content tables and fails closed on any leftover. The promote runner's own post-check is unchanged: it still requires empty read models and unchanged bookkeeping. Every other check (manifest state, ledger, all 94 tables, MLB count, grant) is unchanged, and an unexpected read-model change fails in every lifecycle.

Operations other than promote check the manifest's state first (withdraw/emergency need PROMOTED; finish/revert need EMERGENCY) and then make one database call (atomic); `withdraw` and `finish` are followed by the best-effort `VACUUM (ANALYZE)` of the promoted tables and the read-model tables (its failure is reported, never hidden). `status`, `verify-promoted`, `check-authorization` and `draft-authorization` write nothing to the database.

## 6. Exposure audit: what a promotion publishes immediately

Audited from the catalog and confirmed empirically on the full-scale rehearsal (real PostgREST for the Data API, the real page queries for the website role):

* **Data API (anon, authenticated):** the eight relations closed by migrations 033/034 (`players`, `player_external_ids`, `source_observations`, `coverage_assessments`, `v_draft_explorer`, `v_player_outcome_status`, `v_source_attribution`, `player_aliases`) stay refused (401/403) for GET and for the `exact`, `planned` and `estimated` count modes, before and after the promotion. The only change a Data API client can see is **`public.sources` +1 row** (the Retrosheet source, with the verbatim statement in its notes) and the owner-rights aggregate `v_transaction_record_sources` (its content is unchanged because it counts the empty transaction read model). `transactions`, `trade_packages`, `trade_package_assets` and the staging tables are closed to the roles. The runner computes this set and requires the owner to acknowledge it exactly.
* **Website role (`bai_site`):** reads the new identities at commit; the runner computes this set as well (direct and column-level grants, views over views, inheritance) and the owner's signed file must list it: `coverage_assessments` 360, `player_external_ids` 10,987, `players` 3,643, `source_observations` 7,286, `sources` 1 and the aggregate view (rehearsal). In the rehearsal exactly two of the 23 page queries changed (`getPlayers`, `getSourceAttribution`); the transaction pages stay empty until a read-model refresh (R7), which a promotion never triggers (verified: read-model rows and bookkeeping unchanged).
* **Not exposed (earlier read-only observations on the hosted project, not re-checked by the runner and not part of the rehearsal):** pg_graphql is not installed; the realtime publication has no members; the `ingest` schema is not part of the Data API. SECURITY DEFINER functions executable by the Data API roles are covered by the repository's security audit (`security.mjs`), not by this runner.
* **Method limits:** the audit reads grants and view definitions at preflight; the database does not re-check them inside the promotion transaction, so a grant added between the preflight and the write would be seen only by `verify-promoted`.
* **Unchanged by design:** the free-text player names in `international_signings.notes` (266 rows) and `sources.title` (8 rows): neither table is in the promotion delta (`international_signings` is unchanged, `sources` gains one row).

## 8. Release prerequisites that remain (all owner-gated)

1. **Owner signing key** made and pinned (section 3); public keyring placed on the runner host.
2. **B4** at migration 034 (full backup cycle, new owner authorization), and a promotion parity record from `final-parity.mjs --promotion-package <dir> --offsite-record <backup-run record> --offsite-recipient <owner key>` (the runner refuses a record made from bare hashes).
3. **Live attribution evidence** captured shortly before (≤ 72 h at promotion) from the production deployment.
4. **Package rebuilt from the B4 restore** (the rehearsal manifest is invalid for production), reconciliation report reviewed by the owner, `draft-authorization` output reviewed and signed.
5. **Freeze:** no imports, research writes, refreshes or grant changes between B4 and the promotion.
6. **Operational decisions:** (a) a revert or finish after an emergency leaves the RETROSHEET grant deleted, to be recorded again by the owner; (b) emergency close-api takes four website pages and the Sources Data API endpoint offline until `finish`; (c) the promotion makes the new identities public on the website at commit while the transaction pages stay empty until R7; (d) the 65 MLB trades stay withheld; (e) the free-text names in `international_signings.notes` and `sources.title` are unchanged and need a separate owner decision before the identities are described as complete.
7. **Timing of the signing step:** the signed authorization names the SHA-256 of the parity record, and the parity record is valid for ten minutes, so `final-parity` → `draft-authorization` → the owner's review → `gpg --detach-sign` → `promote` must all complete within ten minutes (the runner re-checks the record just before the write). The attribution evidence is a point-in-time observation of a named deployment: a redeploy of the website within the 72 hours could change the live pages and the tool cannot see that.
8. **Preflight does not check** sequences, roles/ACLs/policies/triggers/event triggers, other sessions or long transactions, replication or a synchronous standby (a backend terminated while waiting for synchronous replication has already committed locally), or state outside the 94-table scope that a restore to the backup would lose (`rm_*`, read-model bookkeeping, auth/storage). The database repeats only the 94-table drift check and the attribution age. The post-promotion `verify-promoted` is the after-the-fact check for the rest, and the freeze rule (item 5) is what protects it.
9. The authorization window for the Retrosheet grant lapses after 2027-01-22 (Chadwick review due 2027-01-21); the runner refuses a package whose window has ended.
