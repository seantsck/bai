# G6B: the Data API boundary for raw identities and evidence (migration 033)

**Status: LOCAL IMPLEMENTATION AND DRAFT PR ONLY. NOT AUTHORIZED FOR HOSTED RELEASE.** Nothing here changes a hosted permission. Owner direction (G6A): BAI's public product is the website, not a supported raw-data REST API; Option A (privilege denial, explicit website grants) for raw player identities and evidence.

## What migration 033 changes (exactly)
For `players`, `player_external_ids`, `source_observations`, `coverage_assessments` (tables) and `v_draft_explorer`, `v_player_outcome_status`, `v_source_attribution` (views that read them and were granted to the Data API roles):

| | before (032 stage) | after 033 |
|---|---|---|
| `anon`, `authenticated`, `PUBLIC` | `SELECT` (anon/authenticated) | **none** (`REVOKE ALL`) |
| `bai_site` (website role) | `SELECT` only through its membership in `anon` | **explicit `GRANT SELECT`** |
| row-level policy on the 4 tables | `public_read` (anon, authenticated) | `site_read` (bai_site) only |
| `public.internal_objects` | not registered | the 7 registered, so every later `apply_public_boundary()` (re-run by earlier and future migrations; it re-grants SELECT to anon/authenticated on any relation not registered) keeps them closed |

**A consequence found while testing, and fixed in 033 (section 3).** 032's emergency procedure found who can read a table with `has_table_privilege('anon'/'authenticated')` and assumed the website role reads "through anon". After the grants above the website role holds its own grant on seven relations, and the unchanged 032 procedure would have (a) left observations that name a promoted player readable by the website during a hide-mode emergency, and (b) not revoked the website's grant in close-api mode. 033 therefore adds `ingest.promotion_readers()` (the website role counts as a reader when it holds the grant directly) and replaces `ingest.emergency_withdraw` (same signature, owner and ACL; hide policies now name `anon, authenticated, bai_site`; close revokes from exactly the roles that held the privilege and records them, so `promotion_reopen`, `revert_emergency` and `finish_withdrawal` are unchanged and give back exactly those). For every table whose readers are anon and authenticated the behaviour is that of 032. Tested at both stages (`promotion-indirect.test.mjs` at 032, `promotion-indirect-033.test.mjs` at 033; the second fails against the unreplaced 032 function).

Kept readable by the Data API roles, by audit: `sources` (the credit, the verbatim Retrosheet statement in `notes`, the source URLs; no identity or evidence rows) and `source_attribution_statements` (the notice link). Not touched: migrations 001-032, raw data, the import batches, the promotion records, `service_role` (bypasses row-level security by design), the owner, `bai_web`, any function (none is executable by the Data API roles).

Why privilege denial and not row-level security: a role without `SELECT` is refused before any plan runs, so `Prefer: count=planned|estimated` cannot reveal how many rows exist (the G5 finding). The views are `security_invoker`: they read the tables with the caller's rights, so no view can open what the tables close; their own `SELECT` is revoked too so that the refusal is a clean 401/403, not a failure inside the view.

## Pre-implementation audit (local restore of the October 31 backup + 032)
* **Website path:** the site never calls the REST API. `lib/db.ts` connects with `pg` and runs each page query as `set local role $BAI_PUBLIC_ROLE` (default `anon`). With `BAI_PUBLIC_ROLE=bai_site` it reads every relation above as `bai_site`. **With the default `anon`, 8 of the 23 page queries fail after 033** (the three closed relations' pages, and the transaction pages which 032 already closes to `anon`): `BAI_PUBLIC_ROLE=bai_site` must be live before 033.
* **Grants / RLS / views:** the four tables had `SELECT` for `anon` and `authenticated` and a `public_read` policy; no column grants. Three further views over them were readable by `anon`/`authenticated`; the other 15 dependent views (analytics, research, internal) are owner-only. All dependent views are `security_invoker`.
* **RPC / SECURITY DEFINER:** no function in `public` or `ingest` is executable by `anon`, `authenticated` or PUBLIC (`apply_public_boundary()` revokes it; default privileges grant functions to the owner only). The SECURITY DEFINER functions are trigger or event-trigger handlers, not callable over REST.
* **Role memberships:** `authenticator` is a member of `anon` and `authenticated` only; it is not a member of `bai_site`, `bai_web` or `postgres`, so the Data API cannot `SET ROLE bai_site` (tested with the real login role and with JWT `role` claims `bai_site`, `postgres`, `bai_web`, `supabase_admin`, `service_role`: all refused). `bai_web` has `SET` (no inherit) on `bai_site`; `bai_site` is a member of `anon` (inherit).
* **Other surfaces:** the backup shows no `pg_graphql` extension (no GraphQL schema) and a `supabase_realtime` publication with no tables; default privileges are for `postgres` only. **Re-check these three on hosted, read-only, before 033.**
* **Repository consumers of direct anon REST:** none for these relations. `scripts/db/lib/security-audit.mjs` probes the Data API with the publishable key but its positive control is `organizations`, and its other probes assert refusals; nothing reads the seven relations. External consumers cannot be known from the repository: before 033, read the hosted API logs (read-only) for requests to `/rest/v1/players`, `player_external_ids`, `source_observations`, `coverage_assessments`, `v_draft_explorer`, `v_player_outcome_status`, `v_source_attribution`. **A known required external consumer would block 033.**
* **Impact on baseline records:** the public REST surface loses 1,612 players, 3,318 identifiers, 12,732 observations, 175 coverage assessments and the three views (1,291 draft-explorer rows, 1,612 outcome-status rows, 18 attribution-summary rows). The website is unchanged: every one of its 23 page queries returns byte-identical results as `bai_site` before and after (measured on the restored baseline and on the preserved full-size promoted copy).
* **Open findings (not in the authorized list; not changed):** (1) `player_aliases` is still readable by `anon` and holds alias text (7 rows today; none for the Retrosheet-created players) and more than 20 other readable tables carry `player_id`, so a caller can still see that a player id exists and facts keyed by it, but not a name or birth date; (2) `rm_overview.players` and `rm_coverage_summary` publish aggregate counts. Decide whether to add `player_aliases` to the closed set (same pattern, a further migration).

4. Verify baseline website functionality as `bai_site`: every page route answers, and `tests/support/page-queries.mjs` hashes equal the pre-032 website's.
5. Migration 033 (this one): 7 relations, milliseconds; `lock_timeout` about 5 s; quiet window.

Verify, before any promotion: read-only security audit; the REST denial matrix (GET only, publishable key) for the seven relations in all three count modes and HEAD; `sources`, `source_attribution_statements`, `organizations` still answer; every page route and the page-query hashes unchanged; the Sources and Players pages carry the Retrosheet statement.
7. Only then prepare the separately authorized Retrosheet publication (G6).

## Recovery if 033 causes an unexpected website or REST failure
* A failure inside the migration rolls back (one transaction): nothing to do; the state is the 032 stage.
* After commit, first rule out configuration: `BAI_PUBLIC_ROLE` really is `bai_site` in the running deployment and `bai_web` can `SET ROLE bai_site` (`select pg_has_role('bai_web','bai_site','member')`). A wrong role setting is fixed in the environment, not in the database.
* If the database change itself must be undone: run `docs/transactions/g6b-rollback-033.sql` (one transaction, `lock_timeout` 5 s). It restores exactly the 032-stage ACLs, policies and registry rows (tested against a database that never had 033) and **reopens the Data API to raw identities and evidence**, so it needs the owner's authorization and a plan to close again. It leaves the ledger row; the correction is a new migration 034, never an edit of 033.
* Last resort for data loss (none is expected: 033 changes privileges, policies and 7 registry rows only): the pre-032 verified backup.
* After any recovery: security audit (read-only), the page routes, and the REST matrix.
