# G5 — off-hosted staging, atomic promotion and withdrawal (migration 032)

**Status: LOCAL IMPLEMENTATION ONLY. NOT AUTHORIZED FOR HOSTED RELEASE.** Nothing in this document, in migration 032 or in `scripts/db/promotion.mjs` authorizes a hosted migration, import, promotion, refresh, grant change or deployment. Every command of the tool refuses a hosted database, and `--hosted` is refused. A hosted release needs the G6 gate, a fresh verified baseline backup and the owner's written authorization for that window. The separate, gated hosted runner and its authorization contract are described in `docs/transactions/g6-hosted-promotion-runner.md`; it is development-only and refuses every write until the owner pins a signing key.

This replaces the hold-in-place design of the closed PR #62 (display-release table, row-level hiding, pre-request count guard). That design cannot be made leak-free: PostgREST answers `Prefer: count=planned|estimated` from the planner's estimate for the whole table, hidden rows included, and a request that repeats the `Prefer` header reaches PostgREST past a pre-request guard (confirmed on the hosted gateway, read-only). So **no row is ever held in a public table**: rows are staged off-hosted and enter the hosted database, in one transaction, only when they are meant to be public.

## Owner decisions (G5-4) recorded here

1. Retrosheet-derived identity information may eventually be public, conditional on explicit, prominent attribution. Source citation alone is not proof of compliance.
2. The Retrosheet `transaction_date` observations (602 on the real data) are **excluded** from the public delta. Their evidence is kept privately with the promotion, and the exclusion is recorded in the manifest (rule, count, ids, SHA-256 of the withheld rows).
3. The 360 coverage rows and the relevant summary models are in the intended public release, conditional on clear PARTIAL labelling, website attribution and an approved direct REST attribution policy (open: see the inventory below).
4. The 65 MLB-sourced trades stay withheld (no MLB grant; unchanged logic).
5. The two Jake Fox identities and the two held T2 collisions are preserved (the importer already holds them; the delta builder refuses to proceed if a baseline row changes).

## How it works

1. **Stage** (off-hosted). Restore a fresh verified baseline backup into a local database, apply migration 032 to it, and import the six pinned batches with the existing importer. Nothing in this tool imports, and the six pinned candidate files are never read or changed here; only their SHA-256 (from `ingest.import_batches`) go into the manifest, and `expectBatches` pins them.
2. **Package** (`scripts/db/promotion.mjs package`). `buildPackage` compares the staged database with the baseline row by row and refuses unless the staging changed no baseline row (the delta is insert-only). It then makes a *release candidate* copy of the staged database, appends the verbatim attribution statement to the notes of the sources the release adds, deletes the excluded rows (the database itself proves nothing else refers to them: a foreign key stops the delete and the build is refused), and computes the delta again. The package is a directory: `manifest.json`, `payload/<table>.json`, `withheld/<table>.json`, `PACKAGE.sha256.json`. The manifest (canonical JSON, named by its SHA-256) pins: the archive, every batch file hash, the migration checksums, the authorization window and the grant binding, the statement hash and the live-page verification evidence, the baseline fingerprint of every table in scope, the release-state fingerprint of every changed table, the load order, the sequences, the exclusions and the annotation. `verify` re-checks a package offline.
3. **Review.** The owner reviews the package (counts, exclusions, hashes) and the staging results. Nothing is public yet.
4. **Promote** (one owner transaction): `promote_begin` (permission, attribution, schema level, write locks on every table in scope, exact baseline drift check), `promote_load` (once per table, explicit primary keys, no `ON CONFLICT`), `promote_withhold` (the private evidence), `promote_commit` (every table equals the staged release state, the batches are exactly the manifest's, the statement is in every promoted source of the category; then the ledger and the event; the sequences move forward last). Any failure or lost connection aborts everything. After a lost acknowledgement the tool asks the ledger (`promotion_status`) and never repeats a committed promotion.
5. **Publish** is separate and unchanged: the grant (025/030) and the owner's refresh (`refresh_read_models`, `refresh_transaction_read_models`). A promotion publishes no transaction by itself.

## Withdrawal

* **Normal** (`withdraw`): one transaction. Refuses while any row that is not part of the promotion depends on a promoted row (a foreign key from any schema, or an observation or decision that names a promoted player or transaction by subject). Withdraws the read model (and proves it clean), deletes exactly the ledger rows (each count checked), optionally the grant, recomputes every summary, and **analyzes every table it changed, last, in the same transaction** (see *Counts in the Data API* below). Existing rows, players that received new ids, and the MLB records are untouched; ids of withdrawn rows are never reused; the withheld evidence is kept.
* **Emergency** (`emergency`): for when public exposure must stop now and the deletion is blocked. In one transaction it withdraws the read model, **deletes the category's grant** (nothing can republish it), empties the cached summaries that count promoted rows, makes every refresh fail until resolved, and **hides the promoted rows** from `anon`, `authenticated` and the website role with a RESTRICTIVE row-level policy per readable table. It deletes nothing and records what it did and the blockers. Resolve with `finish` (after the blockers are removed: deletes the rows, drops the policies, recomputes) or `revert` (false alarm: lifts the hiding; republishes nothing; the grant must be recorded again deliberately).
  * **Indirect references (G5-5C).** A publicly readable row that is *not* part of the promotion but points at a promoted row reveals the withdrawn identity (the player id, and an alias's text; the source id): an alias of a promoted player, an academy citing the promoted source, an observation naming a promoted player or transaction by subject, any table with a foreign key to a promoted row. The emergency finds them with the same dependency scan that blocks a normal withdrawal and **hides them as well** (a restrictive policy on the referencing column or on `subject_table`/`subject_id`), or, when a policy cannot do it (no row-level security on the table, a composite key) or with `--close-api`, **closes their table** to the Data API roles and records the roles so that finish or revert gives back exactly what was taken. The rows are neither deleted nor changed, they block `finish` until the owner removes or re-points them, and unrelated rows that do not reference a promoted row stay readable (hide mode). Tests: `tests/db/promotion-indirect.test.mjs` (SQL, every role, a generic scan of every readable relation including views) and `tests/db/promotion-rest.test.mjs` (real PostgREST, exact/planned/estimated, every readable table and view). What the database cannot see is a reference with no foreign key and no subject link (a name or id inside free text); those are not found.
  * **Trade-off, stated.** Hiding stops reads of the rows, but the Data API's planner-based counts (`Prefer: count=planned|estimated`) still include the hidden rows until they are deleted (the hidden rows are still live rows, so `ANALYZE` cannot help). `emergency --close-api` closes every readable table that held a promoted row, **and every table that holds an indirect reference to one**, to the Data API roles *and* the website role altogether: that **temporarily disables those public endpoints** (players, ids, observations, coverage, sources, and, with them, the views over them: the draft explorer, outcome status, selection attribution and the source attribution summary; on the website the players, draft picks, international signings and sources pages error until the emergency is resolved) and so needs the owner's explicit authorization at the time. `service_role` bypasses row-level security by design and is not covered.
  * The unrelated rows are never cascade-deleted, in either mode.

## Counts in the Data API (G5-5C)

`Prefer: count=planned` (and `count=estimated` whenever the estimate is large) is answered from the planner's estimate, `pg_class.reltuples` and the column statistics, which a `DELETE` does not change until `ANALYZE`. Measured against a real PostgREST (`tests/db/promotion-counts.test.mjs`): after a withdrawal without `ANALYZE` the exact count falls but planned and estimated keep the pre-withdrawal size, so a client reads how many rows were withdrawn (G5-5B: 5,255 players against 1,612).

`ingest.withdraw_promotion` and `ingest.finish_withdrawal` therefore call `ingest.promotion_analyze` **last, inside their own transaction**, on every ledger table and on the four cached summaries, and roll back if an estimate still over-states the live row count. Observed with concurrent independent clients (anon and authenticated, all three modes, both orders of a duplicated `Prefer` header, which PostgREST resolves to the first): the column statistics and the deletes become visible together at `COMMIT` (exact and estimated flip there); `reltuples` is updated *in place*, so `count=planned` shows the new, smaller size slightly before the commit (an under-count of rows that are still readable, never an over-count). A withdrawal that fails after its `ANALYZE` leaves `count=planned` under-stated until the next `ANALYZE`: the tool repairs it at once (`analyzeStatistics`, also `promotion.mjs analyze`), and a lost connection is repaired by running that command. No temporary endpoint closure and no website outage is needed for a normal withdrawal. Hiding (emergency without `--close-api`) cannot use this; closing can.


## The website role and the Data API

Migration 032 adds `bai_site` (NOLOGIN, member of `anon` only, no write privilege, no RLS bypass, no administrative right). `bai_web` may `SET ROLE bai_site`. `anon` and `authenticated` lose `SELECT` on the **10** of the 12 `rm_transaction*` tables they could read (the other two, `rm_transaction_refreshes` and `rm_transaction_withdrawals`, were already closed); the tables are registered in `internal_objects`, so `apply_public_boundary()` keeps them closed. `bai_site` gets `SELECT` on those 10 and its own `site_read` policy.

* **No application code changes.** `lib/db.ts` already reads `BAI_PUBLIC_ROLE`. Set `BAI_PUBLIC_ROLE=bai_site` in the production environment and redeploy. **Order matters**: the migration (role and grants) first, then the environment variable and the deployment. Before the variable is set, the old role (`anon`) cannot read the three transaction page queries. Tests show every one of the 23 existing no-argument page queries returns the same result under `bai_site` on the baseline.
* **`v_transaction_record_sources`** is the one owner-rights view (`security_invoker = false`). It aggregates `rm_transaction_sources` alone (category, record count, source count) so that `v_source_attribution` (030, again `security_invoker`, same content) keeps working for Data API consumers without access to the closed table. Review: it reads exactly `rm_transaction_sources` and `sources` (the security audit enforces this), shows no row, id or name beyond the category, and is empty the moment the read model is withdrawn. The withdrawal analyzes the table it aggregates, so its planner statistics are current at the commit (see *Counts in the Data API*).
* The security audit is amended for exactly this: the declared owner-rights view, the `bai_site` policies on registered-internal tables, `bai_web` membership of `anon` and `bai_site`, and a `bai_site` block (no login, no write, no private schema, no internal table other than the transaction read models).

## Known limitations

* A promoted row is public in the Data API the moment the transaction commits, by design; nothing is held. Public exposure is therefore decided at promotion, not at refresh.
* The delta is deterministic apart from recorded timestamps and the random `players.player_key` UUIDs, so two stagings are not byte-identical; the manifest pins one concrete staged delta.
* The emergency hide mode leaves planner-estimate disclosure (above); the close mode disables endpoints.
* `rm_transactions.search_tsv` is now built in a fixed order (G5-5C; section 6c of the migration): two refreshes of identical data produce identical vectors, so a reconciliation can compare them byte for byte. Before, the order of the player names followed the physical row order of `rm_transaction_players` and the lexeme *positions* differed (314 of 11,257 rows when only that order changed); the set of lexemes was always identical.
* Planner statistics left by an emptied-then-refilled read model: a table that is analyzed while empty (or empty and bloated) leaves the planner without a row estimate, and it then picks a full index scan over the primary key for `where transaction_id = ...`. Measured at full scale this made the per-row probe of the withdrawal triggers 0.74 ms instead of 0.01 ms (the 54 s emergency finish) and the refresh 6 times slower; the finish now skips the probe once the read model is proven clean, and the tool runs `VACUUM (ANALYZE)` on the promoted tables and the `rm_*` tables right after a committed withdrawal or finish (it cannot run inside the transaction) so that the next refresh starts from sound statistics: measured on 33,000 promoted rows, the next transaction refresh took 3.4 s on the statistics the in-transaction `ANALYZE` leaves over a bloated heap and 0.4 s after the vacuum. Without the tool (hosted autovacuum alone) the vacuum happens when the autovacuum thresholds are met.
* The emergency and the refresh block rely on triggers on the summary tables; a different, future refresh function that writes elsewhere must be added to that list.
* The tool and the tests are local. Behaviour on the hosted database (statement timeouts through the pooler, per-row trigger cost at full scale, fingerprint portability between a restored backup and hosted) is **unverified**.
* The real-PostgREST tests skip, loudly, without a binary (`BAI_POSTGREST_BIN`); CI skips them.

## Staging restore and release safety (G5-5E; local tooling only, NOT a release authorization)

**Authoritative staging method: `scripts/db/restore-export.mjs`** (library `scripts/db/lib/export-restore.mjs`), the restore of the backup's *logical export* (`roles.sql`, `schema.sql`, `data.sql`) into a fresh, local PostgreSQL 17. `restore-snapshot.mjs` stays what it was, a row-level check of the snapshot, and is **not** a staging baseline: it rebuilds the schema from the committed migrations and loads rows, so it sets every sequence to the highest id in its table (16 of hosted's sequences differed: `sources` 3790 against 4132, `drafts` 12 against 398, …) and re-applies the migration ledger (`applied_at` = restore time). Staging ids assigned from such a sequence can re-issue ids that hosted used and deleted. The logical export carries both exactly, so the tool needs no change to the backup format.

What `restore-export.mjs` does and proves (every item must pass, or it exits 1 with the problems):
* stand-in roles, then `roles.sql`, `schema.sql`, `data.sql` (which sets `session_replication_role = replica`) through `psql`; each error must be a known platform-only class (Supabase extensions, `auth`/`storage` tables, the realtime publication, BAI's cluster-wide roles already present on a reused server);
* **rows**: every table equals the checksummed snapshot (`hosted-preflight`);
* **sequences**: every BAI sequence equals the export's `setval` (value and called/not called);
* **migration history**: the ledger is exactly migrations 001..030 with their committed checksums, the CLI history in the export matches, and every `applied_at` precedes the moment the export was taken (so it was restored, not re-applied);
* **catalog**: the BAI catalog equals a reference built from the migrations except for explained platform/pg_dump differences (`explainCatalog`);
* `--hosted-state <json>` (the read-only collector's record of hosted, taken in the same database snapshot as the backup): every promotion-scope table fingerprint (count + md5 of every row, 94 tables), every sequence and the grant rows (microsecond precision) equal hosted;
* `--audit`: the full and the read-only security audit on the result.

**Security audit and the Supabase platform.** The export contains `public.rls_auto_enable()` (SECURITY DEFINER, Supabase's) but `pg_dump` does not write its event trigger `ensure_rls` (`ddl_command_end`, tags `CREATE TABLE | CREATE TABLE AS | SELECT INTO`; observed read-only on hosted, 2026-10-31). The audit skips a function only if it is an event-trigger handler, so on a plain restore it correctly reported the function. The restore re-creates exactly that trigger (`PLATFORM_EVENT_TRIGGERS`), **after** the data load. Nothing is suppressed globally, and the strategy is checked independently three ways (`tests/db/restore-export.test.mjs`): (1) the restore tool fails if the restored database has any event-trigger handler other than `public.rls_auto_enable()` (the audit would otherwise skip it silently); (2) a rogue SECURITY DEFINER function in `public` still fails the audit with the trigger present, and without the trigger the audit fails on `rls_auto_enable` itself; (3) the function set (definition hashes, SECURITY DEFINER flags, privileges) equals hosted's in the full comparison with the collector record. `ensure_rls` acts only on tables created in schema `public`; migration 032 creates none there (its four tables are in `ingest`), so the trigger does not alter 032 on hosted either. Roles are cluster-wide: a server that already ran 032 holds `bai_site`, so the authoritative restore uses a fresh server.

**What the backup may still be used for.** The six-hour *eligibility* of a backup (`MAX_BACKUP_AGE_MS`, ends 2026-11-01T03:34:22Z for `g1-20261031T213422Z`) governs a hosted push through `final-parity`. After it expires the backup remains a verified, encrypted archive and may be restored for **local** rehearsal and for building and reviewing a package, but it says nothing about the *current* hosted state: hosted can have changed since. A package built from it is only a candidate.

**At the eventual release** (separately authorized, G6): take a fresh production backup with `backup-run.mjs all`, immediately run the read-only collector on hosted and require it to equal the restore of *that* backup (rows, sequences, grants, ledger, `pg_current_snapshot` unchanged between the collector and the backup, i.e. no transaction consumed), and require the promotion's own drift check (`promote_begin`) to pass; any difference stops the release.

**Migration 032 on hosted: locks and rollback.** `apply_public_boundary()` and the policy and grant changes take ACCESS EXCLUSIVE locks on 94 relations and hold them until commit (measured on the restore: 56-75 ms for the whole file, index builds 1-5 ms; `trade_package_assets` has 111 rows, `transaction_source_links` none). Hosted adds round trips; the figure to rely on is the lock hold, not the CPU time. Requirements: run it in a quiet window; set `lock_timeout` (for example 5 s) on the migrating session so that it fails fast instead of queueing behind a long reader and then blocking every later reader of those tables; keep `statement_timeout` at or above the hosted default of 2 minutes; the file runs as ONE transaction, so any failure (a lock timeout included) rolls back to level 030 completely; after commit there is no down-migration, the objects are additive, the two replaced 030 functions are restored by re-creating them from `030`, and the recovery path is the fresh backup.

**Deployment coordination.** `bai_site` and the website's `BAI_PUBLIC_ROLE=bai_site` must be rolled out in this order: (1) the migration (creates the role and lets `bai_web` `SET ROLE` it; at the same moment `anon` loses `SELECT` on the ten `rm_transaction*` tables the Data API could read); (2) set `BAI_PUBLIC_ROLE=bai_site` in the production environment and redeploy. Setting the variable first makes every page query fail (`SET ROLE bai_site` on a role that does not exist); between (1) and (2) the transaction pages cannot read their (still empty) read model as `anon`, so the window should be minutes, announced, and (2) prepared in advance. The restore tooling does not exercise the deployment; the tests do (`promotion.test.mjs`: the 23 page queries under `bai_site` equal those under `anon` on the baseline).
